# physmerge for SAS

A port of the physmerge R package to Base SAS. It produces the same block
table as `physical_merge()` in R and as the `physmerge` command-line tool, and
`physmerge_selftest.sas` checks that claim against vectors generated by the R
code.

Base SAS only: no SAS/STAT, no SAS/ACCESS, no PROC FCMP. Written against
SAS 9.4; nothing in it is 9.4-specific, so SAS Viya and SAS OnDemand should
both run it.

## Status

The code has **not yet been executed on a SAS installation** -- there is no SAS
on the machine it was written on. The algorithm itself is not in doubt: it is a
line-by-line transliteration of `R/physical_merge.R`, and the same
transliteration into C was checked against R on 400 randomised inputs with zero
disagreements. What has not been checked is the SAS *syntax*. Run
`physmerge_selftest.sas` first; it is designed to tell you in one line whether
the port is faithful.

## Quick start

```sas
%let PMDIR = /path/to/physmerge_pkg/sas;
%include "&PMDIR/physmerge.sas";

/* 1. read a PLINK2 .glm file (gunzip it first; SAS cannot read .gz directly) */
%pm_read(path=/data/height.glm.linear, out=ss, format=plink2);

/* 2. merge */
%physmerge(data=ss, out=blocks,
           sig_th=5e-8, window=500000, reward=min, reset_on=best,
           chrom=&pm_chrom_var, pos=POSITION, value=VALUE, id=&pm_id_var);

/* 3. lead-SNP list for PLINK --extract */
%pm_export(blocks=blocks, file=/data/lead_snps.txt);
```

`%pm_read` sets `&pm_chrom_var`, `&pm_pos_var`, `&pm_id_var`, `&pm_value_var`
and `&pm_reward` for you, because PROC IMPORT renames `#CHROM` to `_CHROM`.

## Macros

| Macro | R equivalent |
|---|---|
| `%pm_read` | `read_sumstat()` |
| `%physmerge` | `physical_merge()` |
| `%pm_annotate` | `annotate_blocks()` |
| `%pm_export` | `export_snp_list()` |
| `%pm_col`, `%pm_vtype`, `%pm_nobs`, `%pm_prep` | internal helpers |

`%physmerge` takes the same arguments as the R function: `sig_th=`, `window=`,
`reward=min|max`, `reset_on=best|any`.

## Validating the port

```sas
%let PMDIR = /path/to/physmerge_pkg/sas;
%include "&PMDIR/physmerge_selftest.sas";
```

It runs 13 cases covering two separated peaks, no significant SNP, a single
SNP, duplicate positions, a one-base window, a long chain of signals under both
`reset_on` rules, three chromosomes including X, `reward=max`, the collapse
pass, a value exactly on the threshold, a run of successive improvements, and
120 random SNPs over two chromosomes. Expected output is
`testdata/vectors_expected.tsv`, written by the R package.

A clean run ends with

```
SELFTEST: PASS (13 cases, 43 blocks).
```

It then checks three guard conditions (`window=0`, a bad `reward`, a bad
`reset_on`), checks that a missing value cannot be mistaken for a significant
one, and checks that an exported numeric id is not written in scientific
notation.

To regenerate the vectors after changing the algorithm, run
`scratchpad/qa/gen_vectors.R` against the R sources.

## Things that behave differently from R, on purpose

**Missing values.** In SAS a missing numeric sorts below every number, so
`value < 5e-8` is true for `.`. Both `%pm_read` and `%pm_prep` drop rows with a
missing position or value before the scan reaches them. Do not feed
`%physmerge` a data set you assembled by hand without that filter.

**Chromosome order.** Chromosomes are ranked by first appearance, not
alphabetically, so that the serial numbers match `physical_merge()`, which
walks `unique(data$CHROM)`. `%pm_prep` sorts by `(first-appearance rank,
position, input row)`, reproducing R's stable `order()`.

**Compressed input.** `%pm_read` cannot read `.gz`. Gunzip first, or use the C
tool, which reads gzip natively.

**Exported ids.** A numeric id is written with `BEST32.`, so position 900000
comes out as `900000`. R's `export_snp_list()` writes `9e+05` here, which PLINK
cannot use -- see the bug list.

**By-chromosome export.** `%pm_export(by_chrom=1)` writes plain
`snp_ch<CHR>.txt` files into `dir=`; it does not zip them, because Base SAS has
no portable zip. The chromosome name is sanitised before it becomes part of a
path, as in the C tool.

## Numeric range: read this before using SAS for p-values

SAS stores numbers as IEEE doubles, but the `BEST32.` informat does not read
subnormals reliably, and on z/OS the native floating-point format underflows
around 1e-78. GWAS p-values routinely go below 1e-300, and a p-value that
underflows to 0 is still "significant", so a merge will usually still be
correct -- but `rps_value` will read 0 and any downstream ranking on it breaks.

If your summary statistics reach that range, merge on `LOG10_P` instead:

```sas
%physmerge(data=ss, out=blocks, value=LOG10_P_NUM,
           sig_th=7.3, reward=max, window=500000, ...);
```

`-log10(5e-8) = 7.301`. This is the same advice `read_sumstat()` gives in R,
and it costs nothing.
